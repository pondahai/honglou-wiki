# 人物生平品質審查:給姊妹專案 agent 的提示詞

本系列（三國演義 / 西遊記 / 封神演義 / 水滸傳 / 紅樓夢 wiki）每一作都是複製前一作再改
`config.py` 與 `characters.py` 而來。好處是方法論一致，代價是**缺陷會遺傳**：寫死在通用腳本
裡的書別用語會原封不動帶到下一本書，而且不會報錯，只會安靜地產出品質較差的內容。

紅樓夢版在 2026-07 做過一次審查，找出六類缺陷。以下提示詞可直接貼給其他專案的 agent。

---

## 貼給 agent 的任務指示

> 這個 repo 是「原著 → Obsidian wiki」自動化專案，管線為
> `fetch_wikisource.py` → `build_wiki.py` → `extract_facts.py`（Map，逐回抽事實）
> → `compose_bios.py`（Reduce，依事實寫人物生平）→ `build_html.py`。
> 它是從姊妹專案複製而來的，請假設**提示詞裡藏有前一本書的殘留**。
>
> 請審查 `vault/人物/*.md` 的生平品質，以及產生它們的兩份 LLM 提示詞
> （`extract_facts.make_prompt`、`compose_bios.make_prompt`）。
>
> 依序做六件事：
>
> 1. **先量化，不要憑印象**。用附錄的偵測腳本跑出每一類缺陷的實際數量與分布頁面，
>    再決定要不要修。有些類別可能在這本書上根本不存在。
> 2. **逐條讀那兩份提示詞，問「這句話是為哪本書寫的」**。凡是舉例、分類、專有名詞，
>    都要對照本書原文驗證。驗證方法是直接數原文出現次數，不要靠印象
>    （紅樓夢版就是這樣發現提示詞在防「菩薩、大仙、老者」，而原文裡後兩者出現 0 次，
>    真正該防的「太太」出現 1911 次）。
> 3. **書別用語一律搬進 `config.py`**，不要留在通用腳本裡。這是這個缺陷家族的根治法，
>    也符合本專案「換書只改 config + characters」的設計。
> 4. **修提示詞，並在 LLM 輸出後面補一層程式檢查**。這是專案核心原則：
>    能用純程式做的絕不用 LLM；必須用 LLM 的，餵齊資料、禁止腦補、要求出處，
>    然後在它的輸出後面再放一層程式檢查。提示詞會被違反，程式檢查不會。
> 5. **先試跑 3 篇再全量**。挑缺陷最嚴重的三個人物，用新提示詞產出但**不寫檔**，
>    確認真的改善了再全量重跑。紅樓夢版試跑時就發現新規則只擋掉四類中的三類。
> 6. **重跑前先備份 `vault/人物/`**，並注意兩階段成本不同（見下方「成本分層」）。
>
> 動手前先把你量到的數字與打算怎麼修講給我聽，我確認後再改。

## 六類缺陷

### A. 前作殘留的書別用語（根因，優先修）

提示詞裡的舉例與分類屬於別本書，對本書空轉，還會把模型往錯的方向帶。

- 紅樓夢版案例一：抽取提示詞要模型小心泛稱「菩薩」「大仙」「老者」——原文中
  `大仙` 0 次、`老者` 0 次。真正的陷阱是「太太」1911 次、「姑娘」1144 次、
  「老太太」975 次，而提示詞從沒提過。
- 紅樓夢版案例二：人物關係節要模型分「師徒、主僕、親屬、盟友、對手」——
  這是三國/西遊的框架。家族小說裡沒有師徒為軸的關係，硬要模型填「對手」欄，
  就填出「對手：無明確清單依據之敵對關係」這種東西。

**修法**：在 `config.py` 新增書別用語，提示詞從 config 讀。

```python
# config.py
GENERIC_APPELLATIONS = [...]   # 本書中大量出現、指涉隨場景而變的身分泛稱
RELATION_KINDS = [...]         # 本書該分的人物關係類別
```

判斷 `GENERIC_APPELLATIONS` 該放什麼：把候選詞拿去數原文出現次數，取高頻且指涉會變的。
判斷 `RELATION_KINDS`：看這本書的社會結構是什麼（家族／江湖／取經團隊／軍政集團）。

### B. 抽取階段的偽事實

抽取提示詞通常有一條「僅被提及名字的人物輸出空陣列」。模型會把它讀成
「要交代一下這個人為什麼無關緊要」，於是產出：

> 「狗兒是本回中僅被提及名字的人物，未登場且無相關情節。」

這條會被原樣抄進「重要事蹟」。紅樓夢版有 42 條、涉及 27 人。

**修法**：提示詞改否定式並舉反例——輸出 `[]`，不得寫「僅被提及」「未登場」之類的說明句，
「他本回沒做什麼」不是事實。**同時**在 `compose_bios.load_facts()` 落地過濾，
這樣不必為了這類問題重跑昂貴的抽取階段。

### C. 撰寫階段的後設字眼

模型把作業術語寫進正文。紅樓夢版有 104 處、分布 18 頁：

> 「籍貫**未在清單中**明確標示」
> 「（**來源：事實清單**）」← 某頁每條事蹟後面都掛
> 「對手：**無明確清單依據**之敵對關係」
> 「（註：**清單僅提及**「太爺」，未提供具體人名）」

「事實清單」是我們的作業術語，讀者根本不知道那是什麼，等於把鷹架留在成品上。

**修法**：三管齊下。(1) 提示詞明講「這是給讀者看的條目，不是工作報告，輸出中不得出現
『清單』『資料』『來源』等指涉作業過程的字眼」；(2) **連提示詞自己的措辭也要改**
（「=== 事實清單 ===」→「=== 逐回內容 ===」），否則模型會把那個詞抄下來；
(3) 擴充程式端的 `META_RE`——原本只抓 `清單未|故不列入|...` 這類特定講法，
模型的變體更多，要抓裸詞。

### D. 百科口吻（跳出書外）

> 「狗兒為**清代小說《紅樓夢》中的人物**」

違反「只能根據事實清單」，且破壞 wiki 的內部視角——其餘頁面都是直接敘事，
只有這幾篇忽然跳出書外。紅樓夢版 3 頁。

**修法**：提示詞加「直接從人物在書中的身分寫起，不要說明他是小說人物，
不要提到作者、朝代、書名」。程式端加偵測**但只用來觸發重試，不要整行剔除**——
那句話通常和開頭段黏在一起，砍掉會連正常敘述一起沒了。

### E. 關係腦補（最嚴重，唯一會產生假資訊的一類）

狗兒頁寫「他娶妻劉氏（即劉姥姥）」、人物關係「**配偶：劉姥姥**」。
原文第 6 回明寫「狗兒遂將**岳母**劉姥姥接來一處過活」——劉姥姥是岳母，妻子是劉氏。

關鍵在於：**事實清單裡沒有任何一條講親屬關係**。這不是抽取階段的錯，是撰寫階段
模型看到「狗兒對劉姥姥……」自行推論的。原提示詞的「清單中沒有的一律不寫」擋不住，
因為模型不覺得那是「清單沒有」，而覺得是「從清單合理得出」。

**修法**：針對性加一條規則——「親屬稱謂只能照抄資料裡的說法，不得由互動推論
（例如資料只說 A 對 B 說話，不可以推論兩人是夫妻、父子）」。紅樓夢版加了這條之後，
同一份事實清單重跑，模型自己把「配偶」改成了「岳母」。

這一類**程式抓不到**，只能靠提示詞 + 人工抽查。審查時請特別重讀所有「人物關係」節的
親屬欄，並拿原文核對至少 5 個人。

### F. 回數出處寫成死連結

提示詞說「每項務必註明回數」但沒規定格式，模型就自作主張寫成 `[[第26回]]`、`[[65回]]`，
而 vault 裡沒有這種頁面，全是死連結。

**修法**：提示詞規定「回數出處一律寫成『（第N回）』的純文字，不可以寫成 [[第N回]] 這種連結」，
程式端再放一道轉換保險絲。轉換要**依位置分兩種**，否則會修出「第（第44回）回」這種東西
（紅樓夢版第一次修補就是這樣壞的）：

- 句中（前面是 在/於/至/自/到/從/第/括號，或後面接 中/時/裡/起）→ 去連結留純文字：
  `在[[第26回]]中` → `在第26回中`
- 句末出處 → 加全形括號，連續多個併成一組：
  `[[66回]][[67回]][[70回]]。` → `（第66回、第67回、第70回）。`

實作見 `compose_bios.fix_chapter_refs()`。改之前務必確認正則不會誤傷有效的回目連結
（`[[第016回 標題…|第16回]]` 這種）。

### G. 結構性缺陷（重生成後才暴露的一批，程式可判定）

大量重生成後，除了 A–F，還會冒出幾類「格式」層面的缺陷。它們不影響單看某頁時的觀感，
但會壞掉連結或漏掉整節，務必納入 audit：

- **名冊傾倒**：模型把幾乎整個人物表塞進「人物關係」節（紅樓夢版香菱一頁塞了上百個名字，
  還編出「封肅（岳父）」等假關係）。徵兆是關係節的頓號「、」極多（正常個位數，退化頁 75~194）。
  原本的退化偵測只抓「同名重複」，抓不到「塞入大量不同名字」，要**另加頓號計數**這條。
- **`}}` 畸形連結**：模型偶爾把 `[[名字]]` 的收尾打成 `[[名字}}`、`[[名字}]`、`[[名字}`。
  只認 `]` 的斷腳修補與偵測都會漏掉，正則要涵蓋 `}`。
- **整節缺漏 / 標題符號打錯**：模型有時只產出「概述＋事蹟」漏掉「人物關係」，
  或把 `### 人物關係` 打成 `=== 人物關係 ===`。要檢查三節標題是否齊全且格式正確，
  缺的觸發重試。

**一個容易自己踩的坑**：如果你的退化偵測是「關係節裡某名字重複 > N 次」，注意**主角自己的名字**
在描述式關係節裡（「薛姨媽：對薛蟠既寵溺又無奈，薛姨媽多方打點…」）會合法地重複很多次。
要排除最高頻的那個名字（幾乎必是主角），只看第二高頻，否則好頁會被誤判成退化、白白重跑。
另外，「關係節 = `bio.split('### 人物關係')[-1]`」在**標題不存在時**會回傳整篇 bio，
把概述與事蹟裡的人名也算進去 → 又一個假退化。先判斷標題在不在。

### 附帶：非人物連結

模型會把地名、物名、未收錄人物也加上 `[[]]`（紅樓夢版 713 處）。
**這一類紅樓夢版決定不處理**——在 Obsidian 裡那是「尚未建立的頁面」而非壞連結，
點下去會提示建立新頁，等於替未來要不要收這些人物先留了記號；日後真的補了人物，
這些連結會自動生效。其他專案可自行決定，但請當成一個獨立決策，不要順手清掉。

## 成本分層（決定要不要重跑）

| 階段 | 規模 | 耗時 | 涵蓋的缺陷 |
|---|---|---|---|
| `extract_facts`（Map） | 全書回數 × 全文 | 數小時 | A（泛稱誤判）、B（偽事實源頭） |
| `compose_bios`（Reduce） | 人物數 | 十幾分鐘 | B、C、D、E、F 全部 |

**建議**：兩份提示詞都修，但通常**只重跑 `compose_bios`**。抽取階段獨有的收穫只有泛稱誤判，
而偽事實可以在落地時用程式濾掉，不必為它重跑數小時。抽取階段的提示詞修改留待下次全量重建生效。

重跑全部人物需要 `--force`（跳過「已有 MARKER 就略過」的邏輯）；紅樓夢版已實作，
其他專案可能要自己加。

## 附錄:偵測腳本

放進 scratchpad 執行，不要進 repo。改 `ROOT` 即可跨專案使用。

```python
# -*- coding: utf-8 -*-
"""六類缺陷的量化盤點;只讀不寫"""
import io, re, sys
from collections import Counter
from pathlib import Path

sys.stdout = io.TextIOWrapper(sys.stdout.buffer, encoding="utf-8")
ROOT = Path(r"...")                      # ← 改成該專案路徑
sys.path.insert(0, str(ROOT / "scripts"))
from compose_bios import load_facts

BIO = re.compile(r"^## 生平$(.*?)^## 出場章回$", re.S | re.M)   # 注意:不能用字串 split,
LINK = re.compile(r"\[\[([^\]|]+)(?:\|[^\]]*)?\]\]")           # "## 生平" 是 "### 生平概述"
NUMISH = re.compile(r"^第?[0-9一二三四五六七八九十百零]+回?$")   # 的子字串,會切錯位置

pages = ({p.stem for p in (ROOT / "vault/人物").glob("*.md")}
         | {p.stem for p in (ROOT / "vault/回目").glob("*.md")})

PATTERNS = {
    "C 後設字眼": re.compile(r"清單|資料|來源：|依據：|未見記載|未明確|無從得知|所提供"),
    "D 百科口吻": re.compile(r"清代|明代|元代|小說《|中的(?:虛構)?人物|作者|章回小說"),
}

tot = Counter()
hits = {k: [] for k in PATTERNS}
dead_ch, dead_ent = Counter(), Counter()
for p in sorted((ROOT / "vault/人物").glob("*.md")):
    m = BIO.search(p.read_text(encoding="utf-8"))
    if not m:
        continue
    bio = m.group(1)
    tot["頁"] += 1
    for label, pat in PATTERNS.items():
        for x in pat.finditer(bio):
            hits[label].append((p.stem, bio[max(0, x.start() - 26):x.end() + 18].replace("\n", "")))
    for x in LINK.finditer(bio):
        tot["連結"] += 1
        t = x.group(1)
        if t in pages:
            continue
        (dead_ch if NUMISH.match(t) else dead_ent)[t] += 1

for label in PATTERNS:
    n = hits[label]
    print(f"{label}: {len(n)} 處 / {len({a for a, _ in n})} 頁")
    for a, c in n[:6]:
        print("   -", a, "|", c)
print(f"F 回數型死連結: {sum(dead_ch.values())}  {dead_ch.most_common(5)}")
print(f"  非人物連結(可不處理): {sum(dead_ent.values())}  {dead_ent.most_common(5)}")

# B 偽事實(抽取階段產物)
NON_EVENT = re.compile(r"僅被提及|僅提及|未登場|沒有登場|無相關情節|未實際登場|無具體情節|未參與")
n = [(c, f) for c, rows in load_facts().items() for _, f in rows
     if isinstance(f, str) and NON_EVENT.search(f)]
print(f"B 偽事實: {len(n)} 條 / {len({c for c, _ in n})} 人")

# A 前作殘留:把提示詞裡出現的專有名詞拿去數原文
raw = (ROOT / "data").glob("*_raw.txt")
text = next(raw).read_text(encoding="utf-8")
for w in ["菩薩", "大仙", "老者", "師父", "師兄", "頭領", "哥哥", "太太", "姑娘", "奶奶"]:
    print(f"  原文出現 {text.count(w):>5} 次  {w}")
```

上面只涵蓋程式可判定的類別（B/C/D/F/G）。**E（關係腦補）沒有偵測腳本——程式判斷不了**，
這是整個審查的硬限制:重跑不保證親屬寫對，只能人工重讀「人物關係」節的親屬欄拿原文核對。
紅樓夢版抽查就在狗兒（「板兒（女婿）」實為兒子）與賈寶玉（賈蘭誤作堂弟實為姪子、
巧姐誤作女兒實為姪女、尤氏誤作「連襟岳母」實為堂嫂）各抓到錯誤——**兩個抽樣點都有錯，
意味著錯誤很可能散布在未抽查的頁上**。務必老實告訴使用者:E 類只做到抽樣修正，無法保證全庫乾淨。
發現的錯誤用手動精修（照原著校正），不要為單一錯字重跑整頁（大頁重生成反而可能引入新退化）。

## 驗收標準

- A：提示詞裡的每個舉例都能在本書原文找到足夠出現次數；書別用語都在 `config.py`
- B：偵測腳本回報 0 條
- C：0 處
- D：0 處
- F：0 處（有效的回目連結未被誤傷）
- E：人工抽查 5 人的親屬關係與原文一致
- 全庫無簡體字（`zh_fix.find_simplified`）、`check_bios_done.py` 回報 missing: 0
